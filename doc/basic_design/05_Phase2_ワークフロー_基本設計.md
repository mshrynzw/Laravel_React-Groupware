---

## 1. 目的・スコープ

有給等の申請をデータとして保持し、承認者による承認・却下およびフロー制御を行う。申請内容の可変部分は JSONB で保持する想定。

---

## 2. 機能概要

| 項目 | 内容 |
|------|------|
| requests テーブル（JSONB） | 申請種別、ペイロード、状態、申請者 |
| approvals テーブル | 申請 ID、承認者、承認順、結果、日時 |
| 承認ルール管理 | 申請種別・組織スコープごとに承認者解決ルールを管理 |
| 申請作成 API | 下書き／提出の区別は要件次第 |
| 承認 API | 承認・却下、次承認者への進行 |
| 承認フロー制御ロジック | 多段承認、代理承認はスコープ外なら記載 |
| 申請一覧画面 | 自分の申請／承認待ちの切替 |
| 承認 UI | 詳細表示と承認アクション |

---

## 3. 画面・API（概要）

### 3.1 画面

- 申請一覧・詳細・新規申請
- 承認待ち一覧・承認画面

### 3.2 API（例）

| メソッド | パス（案） | 説明 |
|----------|------------|------|
| GET | `/api/requests` | 一覧 |
| POST | `/api/requests` | 作成 |
| GET | `/api/requests/{id}` | 詳細 |
| POST | `/api/requests/{id}/approve` | 承認 |
| POST | `/api/requests/{id}/reject` | 却下 |

## 4. データモデル（案）

| テーブル | 主な項目 |
|----------|----------|
| `requests` | id, user_id, type, payload (JSONB), status, … |
| `approvals` | id, request_id, approver_user_id, step_order, result, … |
| `approval_rules` | id, name, request_type, scope, priority, is_active, … |
| `approval_rule_versions` | id, approval_rule_id, version_no, conditions (JSONB), steps (JSONB), … |
| `request_rule_resolutions` | id, request_id, approval_rule_id, resolved_steps (JSONB), … |

## 5. 承認者解決ルール方針

### 5.1 権限方針

- 承認ルールの作成・更新・公開・有効化は **admin 以上**のロールのみ実行可能とする。
- 一般社員は承認ルールの閲覧のみ可能（公開範囲は運用で調整）。

### 5.2 ルール定義の基本単位

- ルールは `request_type`（例: `paid_leave`）と `scope`（global/company/group）をキーとして管理する。
- 条件（conditions）と承認ステップ（steps）は JSONB で保持し、将来の申請種別追加に耐える構造とする。
- 複数ルールが一致する場合は **priority の高いルールを優先**する。
- 一致ルールが存在しない場合に備え、申請種別ごとに **フォールバック（デフォルト）ルール**を必須とする。

### 5.3 承認ステップの考え方

- steps は `step_order` 順に評価される多段承認を基本とする。
- 各 step で `assignee_type`（固定ユーザー／ロール／グループ管理者など）を選択できる設計とする。
- 承認時は current step の承認者のみ操作可能とし、承認順の飛ばしを禁止する。

---

## 6. 非機能

- JSONB のスキーマバージョン管理（申請種別ごと）を検討。
- **監査ログ（操作履歴）**: 申請の**作成・更新・提出・取下**、**ステータス変更**、**承認・却下**、payload（JSONB）の**重要な変更**について、**誰が・いつ・どの申請に対して・何を変更したか**を追跡できるよう記録する（承認操作に限らず、業務上の状態遷移をすべて対象とする）。
- **監査ログ（ルール管理）**: 承認ルールの**作成・更新・公開・有効化/無効化**、および申請提出時の**解決結果（どのルール版が適用されたか）**を追跡できるよう記録する。

---

## 7. 依存関係

- **前提**: ユーザー・グループ・承認者の関係が定義できること。
- **連携**: ダッシュボード「未承認申請」、勤怠（有給日数）と連携する場合は別設計。
