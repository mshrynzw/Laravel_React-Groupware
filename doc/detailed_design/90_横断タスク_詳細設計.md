## 3. 共通レスポンス形式

### 3.1 成功（単体リソース）

```json
{
  "data": { }
}
```

### 3.2 成功（一覧・ページング）

```json
{
  "data": [ ],
  "meta": {
    "current_page": 1,
    "per_page": 15,
    "total": 100,
    "last_page": 7
  }
}
```

※ cursor 方式にする場合は `meta.next_cursor` を定義し、クエリ `cursor` で受け取る。

### 3.3 失敗

| HTTP | 用途 |
|------|------|
| 401 | 未認証（トークン欠如・無効） |
| 403 | 認可失敗（ポリシー） |
| 404 | リソース不存在 |
| 422 | バリデーションエラー |
| 429 | レート制限 |
| 500 | サーバ内部エラー（本番では詳細を隠す） |

```json
{
  "message": "人が読む概要",
  "errors": {
    "field_name": ["メッセージ1"]
  }
}
```

業務コードが必要な場合のみ `code` を追加（例: `"code": "PAYROLL_ALREADY_CLOSED"`）。

## 9. データベース共通規約

- 本プロジェクトで定義する **全テーブル** に、次の行を **必須（NOT NULL）** とする。

`| created_at / updated_at | timestamp | NO | |`

- Laravel ではマイグレーションで `$table->timestamps();` を付与し、DB 制約上も NOT NULL とする（`nullableTimestamps()` は使用しない）。

## 12. API ベース・認証方式（エンドポイント別）

| 区分 | パス例 | 認証 |
|------|--------|------|
| ゲスト | `/api/login`, `/api/register`, `/api/forgot-password`, `/api/reset-password` | 不要（`guest` ミドルウェア） |
| 署名付き | `/api/verify-email/{id}/{hash}` | 署名 URL |
| 認証必須 | 上記以外の `/api/*` | **Sanctum SPA Cookie**（`statefulApi()` + `auth:sanctum`）。フロントは `credentials: 'include'` と CSRF（`/sanctum/csrf-cookie`）を使用。Bearer トークン方式に切り替える場合は別途設計更新。 |

---

## 13. HTTP ステータス・バリデーション形式

| HTTP | 用途 |
|------|------|
| 401 | 未認証（セッション無効・未ログイン） |
| 403 | 認可失敗 |
| 404 | リソース不存在 |
| 422 | バリデーション失敗（`FormRequest`）または業務ルール違反（`abort(422, ...)`）。業務コードが必要な場合は `errors` に `code` キーを追加（例: 勤怠打刻）。 |
| 429 | レート制限（メール再送等） |
| 500 | サーバ内部エラー |

Laravel の `ValidationException` は JSON で `message` と `errors`（フィールド名 → メッセージ配列）を返す。横断仕様 §3.3 に整合。

---

## 14. 一覧 API の `data` / `meta`

Laravel `paginate()` の JSON は `data`, `links`, `meta`（`current_page`, `per_page`, `total`, …）を含む。横断 §3.2 の `meta` と**実質同一**であるため、**追加のラッパーは設けない**。単体リソースで `{ "data": ... }` のみを要求するエンドポイントは Phase2 対象外（必要時は個別設計）。

## 15. `X-Request-Id`（相関 ID）

| 項目 | 実装 |
|------|------|
| ミドルウェア | `App\Http\Middleware\AssignRequestId` を `api` ミドルウェアグループに追加。 |
| 入力 | リクエストヘッダ `X-Request-Id` が **UUID** または **英数字・`.` `_` `:` `-` の 8〜128 文字**のときのみ採用。それ以外はサーバ生成 UUID。 |
| 出力 | 全 API レスポンスに同一値を `X-Request-Id` ヘッダで返す。 |
| 監査 | `AuditLogger` が `audit_logs.payload` の先頭に `request_id` をマージ（相関追跡）。 |
| アプリログ | Monolog のグローバル `withContext` は未使用。必要になれば `config/logging.php` でプロセッサ追加を検討。 |

## 16. 認可（Phase2 / Phase3 / Phase4）の所在

| 領域 | 所在 | 備考 |
|------|------|------|
| ワークフロー申請 | `WorkflowRequestController`（閲覧・提出・承認者判定） | Phase2 では **Policy 未導入**。`ensureCanView` 等の private メソッドで認可。 |
| 承認ルール | `ApprovalRuleController` + User の `canManageWorkflowRules()` | |
| 勤怠打刻・参照 | `AttendanceController` + 同一グループスコープ | 打刻は本人のみ。他ユーザー参照は admin/superadmin + グループ重複。 |
| ユーザー・グループ | 各 `*Controller` | 既存の `ensureCanManageUser` 等。 |
| お知らせ | `AnnouncementController` + FormRequest | Phase3 も **Policy 未導入**。 |
| ファイル共有 | `FileController` の `ensureCanAccessFile` + `StoreFileRequest` | 同上。本人・管理者グループスコープ・スーパー管理者は Controller 内で判定。 |
| タスク | `TaskController` の `scopedTasksQuery` / `ensureCan*` | Phase4 も **Policy 未導入**。作成者・担当者・管理者グループスコープ。 |
| スケジュール | `ScheduleController`（勤怠と同様の `user_id` 解決） | 同上。 |
| チャット | `ChatRoomController` / `ChatMessageController` の `ensureMember` 等 | 同上。ルーム参加者のみメッセージ送信可。 |

将来、認可を Policy に集約する場合は `test/Phase2.md`、`test/Phase3.md`、`test/Phase4.md` を更新し、段階的移行とする。

## 17. 監査ログ（`audit_logs`）

### 17.1 対象イベント（Phase2 で記録）

| event プレフィックス | 例 |
|----------------------|-----|
| `auth.*` | login, logout, login_failed, register, … |
| `user.*` | created, updated, deleted |
| `group.*` | created, updated, deleted |
| `request.*` | created, submitted, approved, rejected |
| `workflow_rule.*` | created, updated, published, activated, deactivated |
| `attendance.*` | clock_in, clock_out |

### 17.1a 対象イベント（Phase3 実装時に追加）

| event プレフィックス | 例 |
|----------------------|-----|
| `announcement.*` | created, updated, deleted（`published_at` 変更は `updated` の payload に before/after） |
| `file.*` | uploaded, downloaded, deleted |

詳細は `06_Phase3_お知らせ_詳細設計.md` §10、`07_Phase3_ファイル共有_詳細設計.md` §10 を参照。

### 17.1b 対象イベント（Phase4 実装時に追加）

| event プレフィックス | 例 |
|----------------------|-----|
| `task.*` | created, updated, deleted |
| `schedule.*` | created, updated, deleted |
| `chat.*` | room_created, message_sent |

### 17.2 最低項目

| 項目 | 保存先 |
|------|--------|
| actor | `actor_user_id`（nullable はゲスト操作） |
| action | `event` 文字列 |
| resource | `auditable_type` + `auditable_id` |
| before/after | `payload` JSON（操作ごとに必要な差分・コメント等） |
| timestamp | `created_at` |
| 相関 | `payload.request_id`（`X-Request-Id` が付与されている場合） |

### 17.3 マスキング方針

| データ | 方針 |
|--------|------|
| パスワード | **監査 payload に含めない**（ログイン失敗時は email のみ等）。 |
| トークン | アプリケーションログに生トークンを出さない。 |
| 個人情報 | 監査 `payload` は業務上必要な最小限（例: メールは認証系イベントのみ）。全文検索・デバッグログに個人情報を混ぜない。 |

## 18. API 共通規約との整合（完了条件）

- Phase2 の主要 API は **401/403/422** を結合テストで確認済み。
- 一覧系は **Laravel 標準ページネーション**で `data` + `meta` を提供。
- 監査対象操作は **`AuditLogger::log`** 経由で `audit_logs` に残す。
